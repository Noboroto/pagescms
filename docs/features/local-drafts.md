# Local content drafts

Entry and configuration editors save unsaved content to IndexedDB on the current device after a short debounce. Existing entries restore content, the original file SHA, and the original editable values on reload. New entries retain content and filename, with separate draft identities for independently opened new entries. Drafts are scoped to the signed-in account, repository provider, repository, branch, and entry or creation directory.

The editor waits for its local lookup before enabling editing, with no draft loading message or local-save toast. Entry loading and local draft lookup share two labelled placeholders: a 32px text input and a 128px rich-text area. They use the editor’s Field layout, including 24px label rows (28px with rich-text controls), an 8px gap before controls, and 20px between fields. Once a local draft has been saved, a muted ghost button beside Save (or Create entry) shows its compact age, for example “Just now” or “4m ago”. The age comes from the last successful IndexedDB save, survives reloads, and does not advance when unchanged content is flushed. Clicking it opens a shadcn popover explaining when the draft was saved in this browser and that those changes have not been saved to the project. The popover offers Discard draft and explains that it removes the unsaved changes and restores the last loaded or saved version. Discard remains available when validation disables Save; it does not write to the repository. Recovery errors and download/discard actions remain above the form. Keep the tab open if local storage fails; operations that must flush a draft stop when persistence fails. A configuration mismatch retains the draft and blocks saving until it is discarded or the previous configuration is restored. Concurrent local writes use revision checks and report a conflict rather than overwriting another tab's draft.

Repository Overview lists resumable drafts, recently opened entries, configured collection create shortcuts, and fixed-file edit shortcuts. Its sidebar link uses the Lucide LayoutDashboard icon. Recent visits retain at most 50 records per account, provider, owner, repository and branch when an entry is opened; Overview shows the latest 10 for that scope. Repeat visits update the same entry. Pruning visit records never removes drafts. Both drafts and visits remain local to this browser/device. Overview, editor draft popovers and draft recovery messages share the same shadcn confirmation before discarding. Cancel keeps the unsaved changes; confirming removes the local draft without changing saved project content. Failed discards keep the dialog open with a retryable error. Discard still checks its local revision.

Custom messages are optional: enable `settings.commit.allowCustomMessage`, or override it with `commit.allowCustomMessage` on a content definition. Canceling the message dialog does not write to GitHub.

Save uses the normal single-file GitHub Contents API. A stale write is rejected by its original file SHA and opens a review using freshly fetched GitHub data. Ordinary saves do not add a preflight GitHub read. Existing entries remain editable while saving. The submitted snapshot is the one being committed; later edits remain unsaved in the draft. Successful saves update its baseline and file SHA, immediately persist newer edits with that SHA, and clear the draft only when it matches the committed content. One operation may run per file at a time, with no automatic retry or queue.

## Reviewing concurrent changes

After a save conflict, the comparison dialog compares the original values, the current local draft, and the latest GitHub version. Changes to different plain-object fields, including nested fields, combine automatically. Different edits to the same field require a choice. Lists, polymorphic blocks, rich text and raw source remain whole values; there is no list-item matching, deduplication, reordering inference or text-level merge. Deleting or replacing an object conflicts with another user's edits inside that object.

The comparison uses the shared dialog and its standard typography. Its maximum width is twice the editor's 48rem maximum (96rem); it stays centered within the visible viewport during browser zoom and panning. The title “Some changes need your review” and description explain how many fields need a choice. Headers remain neutral: “Your changes” and “Latest saved version”; the view does not assume who made another save. The internal original values are not shown as a third choice.

Each conflicting field keeps its configured label and nested breadcrumb, for example Author › Email, inside its own read-only field control. Rows have horizontal separators, with no additional borders or selected backgrounds around the comparisons. A radio button sits to the left of each field. Input and textarea previews keep the same background as rich text instead of inheriting disabled-control fills. Both versions start at full opacity; choosing one dims the other field to 50% while keeping its radio visible. The two values stay in aligned columns beneath one sticky version heading per column. Each version heading starts at the left edge of its full column, aligned with the radio rather than the inset field control. Headings, radios and field controls inherit the same CSS grid tracks, with an inset separator. Version selection uses the registry shadcn Radio Group and its built-in keyboard handling. On narrow visible viewports they stack and repeat the version labels above each choice, also starting at the full choice’s left edge. Radios stay beside the actual field labels; version labels are not indented to the field controls. Rich-text spacing ignores ProseMirror cursor decorations when finding the first content element. A gap cursor inserted before a leading image therefore cannot restore its top margin or change the comparison height. Keyboard users can select with Space and move between versions with arrow keys. Values use the existing field controls, including rich text, nested objects and expanded whole lists; structured data is not dumped as JSON. Raw source uses a labelled read-only text area. List items cannot be edited, rearranged or individually selected during comparison. The comparison loads only when review is needed.

“Use all my changes” sits at the right edge of the “Your changes” column header on desktop and at the left edge above the stacked choices on mobile and selects the local version of every conflicting field. Changes outside those conflicts still combine automatically. There is no bulk latest-version action. “Save changes” persists the chosen content against the latest file SHA, then saves through the normal write operation without a second save or commit-message prompt. If the result already matches the latest saved version, no write is needed. An intervening save opens a fresh review with new choices required. Failed saves retain the chosen draft and allow retrying or adjusting choices. Cancel before saving keeps the original draft. The title, description and footer stay pinned. Version headings stick to the top of the comparison scroller, so their columns stay aligned when a scrollbar appears. Short visible viewports use a shorter description and compact footer to retain room for the fields.

Older drafts without original values can use the freshly loaded baseline only if their original SHA still matches. Otherwise review requires choosing a whole version. Failed latest-version reads or changed content configuration retain local edits; they never bypass permissions or file-version checks. Configuration and raw-source conflicts use the same review as one whole source value.

## Navigation and operations

Navigation within the app flushes the latest draft before leaving. The operation continues after its editor unmounts, and reopening the entry shows the same pending save and current edits. A failed operation retains the draft and reports the error. Canonical entry data is returned only when read access is allowed; a read-permission failure after committing does not fail or repeat the write. Confirmed entry data updates the query cache immediately; collection refreshes run in the background and do not extend the save or turn a successful write into a failure.

Closing or reloading the tab can interrupt an in-flight request. Before saving, the draft records the submitted snapshot locally. On reload, a fresh remote file value matching that snapshot at a changed SHA proves it committed and permits rebasing newer edits. Otherwise the original SHA remains in effect and normal conflict protection applies. No server save journal, automatic write retry, or batch commit is used.

Create shows a pending collection row without an entry link until the real path is confirmed. Background creation updates the collection without redirecting a user who already left. Rename displays its proposed filename while retaining the confirmed path; after success it migrates the draft and recent-entry link to the new path. Delete removes its row while pending and restores it on failure. Its confirmation warns about unsaved changes. Rename and delete change local recovery data only after GitHub succeeds and only if its revision still matches. Drafts changed in another tab are retained for download from Overview.

Media uploads occur immediately through the existing upload flow. Drafts contain permanent media references, not pending binary files. Content and media use separate commits. Local drafts are not shared or synchronized across devices. Folder rename and a save-first colocated-media policy are tracked in TODO.

Configuration uses the same draft session and navigation flush as entries, with a separate draft identity for `.pages.yml`. It remains editable while saving; later edits keep the confirmed file SHA. Invalid YAML stays in the local draft and cannot be saved remotely. Configuration changes refresh workspace data in the background after confirmation.

Media browsing remains usable during uploads and file operations. Pending upload/folder rows cannot be selected or opened; rename retains the confirmed path until the response arrives. Pending delete and move overlays affect only their own file, so failure restores that row without undoing other confirmed operations. Confirmed uploads update the directory one file at a time, and partial failures retain successful uploads. Upload files are held only while their request runs, not in IndexedDB. The existing direct-upload confirmation retry remains unchanged; ordinary media mutations do not retry automatically.

Workflow dispatch, cancel/rerun, branch creation, collaborator changes and cache management keep their completion callbacks after navigation. They update confirmed data and refresh in the background. Workflow statuses and collaborator membership are never invented before the server confirms them. Closing a pending dispatch or branch dialog lets the request continue; branch creation redirects only if its original dialog and page are still active. Content, configuration and media writes share a physical-path guard within the current query client. Server file versions remain the conflict protection across tabs and users.

Changing the signed-in account stops remaining upload initiations, transfers and confirmations in a batch; an already submitted request can still finish. Upload progress from the old account is dismissed. Field upload completion merges into the latest selection and callback, preserving intervening edits, and does not modify an editor field after it unmounts. Successfully uploaded assets remain available in Media.

Draft-backed writes remain bound to the account that opened their draft session. They check the current account before and after local persistence, before sending the request. Completion effects recheck the account after asynchronous work; the original account's recovery record is still acknowledged after its confirmed commit. Branch creation redirects only through the still-mounted originating dialog, including when browser history leaves and returns to the same URL. Media lease refreshes affect only the folders touched by the operation.

## Content icons

Collections and fixed files can set an optional `icon` using a Lucide name in kebab-case:

```yaml
content:
  - name: posts
    type: collection
    path: content/posts
    icon: newspaper
  - name: home
    type: file
    path: content/home.md
    icon: house
```

The sidebar and Overview shortcuts use the configured icon. Defaults remain visible while loading and for unknown names or failed loads. The local catalogue lookup and selected icon modules load on demand only when a configured icon is used; no external icon service or full icon picker is loaded by Overview.
